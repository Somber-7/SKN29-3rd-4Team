---

## 1. 테스트 개요

### 목적

- RAG 파이프라인이 사용자 질문에 대해 관련 있는 컨텍스트를 검색하고 그에 근거한 답변을 생성하는지 검증
- 에이전트 라우팅(Tool 선택) 정확도 확인
- 한계점 식별 및 개선 방향 도출

### 평가 방법: LLM-as-a-Judge

GPT-5.4 (full 버전)를 판정 모델로 사용하여 3가지 핵심 지표를 1~5점으로 채점한다.
파이프라인 생성 모델(gpt-5.4-mini)보다 상위 모델을 judge로 사용하여 자기 평가 편향을 최소화했다.

| 지표 | 정의 |
|---|---|
| **Context Relevance** | 검색된 컨텍스트가 사용자 질문에 답하기 위해 필요한 정보를 포함하는가 |
| **Groundedness** | 생성된 답변이 검색 컨텍스트에 근거하는가 (환각 여부) |
| **Answer Relevance** | 생성된 답변이 사용자 질문에 실질적으로 답하는가 |

## 6. 한계점 및 개선 방향

### 한계점 1 — 한자 이름 + 吉수 복합 추천 Groundedness 저하

**현상:** 吉수 획수 조합(sql_db)과 한자 후보(internal_rag) 두 결과가 별도 컨텍스트로 존재하지만 연계되지 않아, LLM이 吉수 획수 조건을 무시하고 hallucinate한다.

**원인:** generate 노드에서 吉수 획수에 맞는 한자 후보 풀을 필터링하지 않고 전체 hanja_col 컨텍스트를 그대로 사용한다.

**개선 방향:** sql_db 吉수 결과에서 획수 조합을 파싱하여 해당 획수의 한자만 verified pool에 포함하는 stroke-filter 로직 추가.

### 한계점 2 — 환각 발생 가능성 (Groundedness 3.82)

**현상:** 한자 이름 추천 시 hanja_col에서 검색된 한자가 아닌 모델 내부 지식의 한자를 사용하는 경우가 발생한다.

**원인:** 성씨 오행 기반 verified pool이 충분하지 않을 때 LLM이 컨텍스트 외 한자를 선택한다.

**개선 방향:** verified pool이 비어 있을 때 generate를 중단하고 추가 검색을 요청하는 fallback 로직 추가.

### 한계점 3 — 복합 조건 요청 시 이름 미생성 (Case 8)

**현상:** 성씨 한자가 불명확하거나 複数 조건(오행 + 吉수 + 뜻)이 동시에 필요한 경우, 정보 수집 후에도 이름을 생성하지 않고 추가 정보를 요청한다.

**원인:** 성씨 한자 미확정 시 verified pool을 구성할 수 없어 안전한 선택(clarify)으로 fallback.

**개선 방향:** 명시된 오행 조건만으로도 generate를 시도하되, 성씨 한자 불명임을 답변 내에서 명시하는 방식으로 UX 개선.
