# Qwen LoRA 파인튜닝 모델 LLM-as-a-Judge 평가 보고서

> 작성일: 2026-06-17
> 시스템: Qwen3.5-4B LoRA 파인튜닝 모델 직접 호출 (RAG 없음)
> 생성 모델: `qwen-lora` (Qwen3.5-4B + LoRA v2) / Judge 모델: `gpt-5.4`

---

## 1. 평가 개요

### 시스템 구성

본 평가는 작명 도메인 데이터(1만 건)로 파인튜닝된 Qwen3.5-4B LoRA 모델을 대상으로 한다. GPT 파이프라인과 달리 RAG 검색이나 외부 도구 없이 사용자 자연어 질의를 모델에 직접 전달하며, 파인튜닝으로 내재화된 지식만으로 답변을 생성한다.

| 항목 | 내용 |
|---|---|
| 생성 모델 | `qwen-lora` (Qwen3.5-4B + LoRA v2) |
| 서빙 환경 | RunPod + Cloudflare Tunnel (vLLM) |
| 호출 방식 | OpenAI 호환 API 직접 호출 (RAG·도구 없음) |
| Judge 모델 | `gpt-5.4` |
| 평가 스크립트 | `tests/qwen_eval.py` |

### 평가 지표

GPT 파이프라인과 달리 검색 컨텍스트가 없으므로 Context Relevance 대신 Factual Accuracy를 사용한다.

| 지표 | 정의 |
|---|---|
| **Factual Accuracy (FA)** | 한자·오행·수리 정보가 실제 사실에 부합하는가 |
| **Groundedness (GR)** | 답변이 구체적 근거(한자 뜻·획수·오행)를 포함하는가 (막연한 추천이 아닌가) |
| **Answer Relevance (AR)** | 생성된 답변이 사용자 질문에 실질적으로 답하는가 |

## 4. 주요 실패 패턴 분석

### 패턴 1 — 수리 계산 불가 (케이스 7)
- **현상**: 81수리 4격(천격·인격·지격·총격) 공식을 적용하지 못하고 추측과 면책 문구로 대체
- **원인**: 파인튜닝 데이터에 수리 계산 절차가 충분히 포함되지 않은 것으로 추정

### 패턴 2 — 오행 관계 오류 (케이스 2, 6)
- **현상**: 목(木)→화(火)를 상극으로 판단, 오행 상생/상극 원리 혼동
- **원인**: 오행 관계표가 파라미터에 일관되게 내재화되지 않음

### 패턴 3 — 순우리말 외자 조건 미충족 (케이스 9, 10)
- **현상**: "외자(1음절)" 요청에 두 음절 이름(하리, 준아, 임고은 등) 생성
- **원인**: 음절 수 제약을 텍스트 조건으로 처리하지 못함

### 패턴 4 — 법령·논문 hallucination (케이스 4, 5)
- **현상**: 실제와 다른 법령명("한글 이름쓰기 규정" 등) 및 출처 없는 통계 생성
- **원인**: 외부 검색 없이 파라미터 내 지식에만 의존, 실제 법령 데이터 미학습

### 패턴 5 — 복합 조건 타임아웃 (케이스 1)
- **현상**: "8획 성씨 + 吉수 + 木오행 + 밝은 뜻" 복합 조건 처리 중 361초 경과 후 타임아웃
- **원인**: 복잡한 제약 조합 처리 시 reasoning loop 발생으로 추정

| 항목 | 결과 |
|---|---|
| 전체 답변 생성 성공률 | **10/11 (91%)** — 케이스 1 타임아웃 |
| LLM-as-a-Judge 종합 평균 | **1.63 / 5.0** |
| 상대적으로 나은 영역 | 이름 형식 추천 (순우리말·한자 형식 준수) |
| 취약 영역 | 수리 계산, 오행 관계, 법령 조문, 외자 조건 |

파인튜닝만으로는 수치 계산, 외부 법령 정보, 오행 관계표 등 구조화된 도메인 지식을 모델 파라미터에 완전히 내재화하기 어렵다. 이름 생성 형식(## [이름 N] 구조)은 파인튜닝으로 학습되었으나, 조건 충족 여부에 대한 정확한 판단은 외부 데이터 참조 없이 달성하기 어렵다.
