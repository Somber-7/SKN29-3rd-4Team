## 1. 전체 아키텍처

```
사용자 입력 (Open WebUI — http://192.168.0.42:3000)
  │
  ▼
[Open WebUI Pipelines] — port 9099, Docker 컨테이너 (naming-pipelines)
  naming_pipeline.py
    _resolve_query()   ← 대화 이력 기반 쿼리 재구성
    app.invoke(state)  ← LangGraph 호출
  │
  ▼
[LangGraph ReAct StateGraph] — naming_graph.py
  진입점: llm_router_node
  │
  ├─► internal_rag  → ChromaDB (rag_server.py)
  ├─► graph_db      → Neo4j    (graph_server.py)
  ├─► sql_db        → SQLite   (db_server.py)
  ├─► external_api  → 외부 API  (law_server.py)
  ├─► clarify       → 반문 생성 후 END
  └─► generate      → 최종 답변 생성 후 END
```

## 3. Open WebUI Pipeline — `pipelines/naming_pipeline.py`

### 역할

Open WebUI의 Pipelines 서버가 호출하는 진입점입니다. 대화 이력을 분석해 그래프에 전달할 최종 쿼리를 구성하고 LangGraph를 실행합니다.

### 주요 메서드

#### `on_startup()`

```python
async def on_startup(self):
    _stub_fastmcp()                      # fastmcp 스텁 주입 (컨테이너 내 MCP 서버 미구동)
    from naming_graph import build_graph
    self.app = build_graph()             # LangGraph 컴파일
```

#### `pipe()`

```python
def pipe(self, user_message, model_id, messages, body) -> str:
    query = self._resolve_query(user_message, messages)
    state = { "query": query, "context": "", "next_action": "generate",
              "answer": "", "iterations": 0, "used_tools": [],
              "collections": [], "name_length": 2, "surname_hanja": "" }
    result = self.app.invoke(state)
    return result.get("answer", "").strip()
```

#### `_resolve_query()` — 쿼리 재구성 3가지 케이스

| 케이스 | 조건 | 처리 |
|---|---|---|
| clarify 응답 | 이전 assistant 메시지에 "아래 정보를 알려주세요" 포함 | 원본 이름 요청 + clarify 답변 + 현재 메시지 합성 |
| 추가 추천 요청 | `_CONTINUATION_KW` 포함 ("더 추천", "2개 더" 등) | 원본 요청에서 개수 교체 + 이미 추천한 이름 제외 지시 |
| 일반 이름 요청 | `_NAME_REQUEST_KW` 포함 + 이전 추천 이력 있음 | 이전 이름과 겹치지 않는 이름 요청 문구 추가 |

## 4. LangGraph StateGraph — `src/graph/naming_graph.py`

### State 정의 (`NamingState`)

```python
class NamingState(TypedDict):
    query: str           # 사용자 원본 질문
    context: str         # 누적된 Tool 실행 결과 (최대 8,000자)
    next_action: str     # LLM이 결정한 다음 액션
    answer: str          # 최종 답변
    iterations: int      # 현재 반복 횟수 (최대 5회)
    used_tools: list     # 이미 실행한 Tool 이력 (중복 방지)
    collections: list    # LLM이 선택한 RAG 컬렉션 목록
    name_length: int     # 이름 글자 수 (1=외자, 2=두글자)
    surname_hanja: str   # 성씨 한자
```

### 노드 및 흐름

```
            ┌─────────────────────────────────────────────┐
            │              llm_router_node                  │
            │  gpt-5.4-mini (temp=0) JSON 한 줄 출력        │
            │  MAX_ITERATIONS=5 초과 시 강제 generate        │
            └──────────────┬──────────────────────────────┘
                           │ route_selector(state)
          ┌────────────────┼──────────────────────┐
          │         │         │         │          │
    internal_rag graph_db sql_db external_api   clarify / generate
          │         │         │         │
          └─────────┴─────────┴─────────┘
                     (ReAct 루프: 실행 후 → llm_router 복귀)
```

### 노드별 상세

#### `llm_router_node`

- `gpt-5.4-mini`, temperature=0, max_tokens=1024
- 첫 진입 시(`iterations==0`) `_resolve_surname(query)` 코드로 성씨 한자 확인
  - 성씨 있는데 한자 미제공 + 한자 이름 요청 → 즉시 `clarify`
- JSON 응답 파싱 → `next_action`, `collections` 추출
- 성씨 한자가 확인됐는데 LLM이 clarify 선택 시 → `internal_rag`로 교정

#### `internal_rag_node`

- 컬렉션별 처리:
  - `paper_col`: 성별 감지 → 트렌드 검색 쿼리 생성 (`_build_paper_query`)
  - `hanja_col`: 요청 개수×8 만큼 한자 샘플링 (최대 80건), 성씨 오행 확인 시 상생 체인으로 분할 샘플링
  - `urimalsam_col`: 성별 필터링 + 랜덤 샘플링 (`sample_urimalsam`)
  - 기타: 시맨틱 검색 (`search_rag`)

#### `graph_db_node`

- Neo4j에서 한자-오행 관계 탐색
- `graph_server.answer_graph_query(query)` 호출

#### `sql_db_node`

- 쿼리 패턴으로 처리 분기:
  - 吉수 역산: `db_server.find_lucky_strokes(획수)`
  - 오행 조합: `db_server.lookup_ohaeng_combo(오1, 오2, 오3)`
  - 3개 숫자 추출 성공: `db_server.calculate_name_suri(s1, s2, s3)`

#### `external_api_node`

- 검증 키워드 → `law_server.verify_korean_word(word)` (우리말샘 API)
- 법령 키워드 → `law_server.search_law(query)` (국가법령정보 API)

#### `clarify_node`

- 누락 항목 판별 후 반문 생성:
  - 성별 없음 → "아들/딸 중 어느 쪽인가요?"
  - 이름 유형 없음 → "한자/순우리말 중 어느 쪽인가요?"
  - 성씨 한자 없음 → "동음이의 성씨 한자를 알려주세요"
- 반문 후 `END`

#### `generate_node`

- `gpt-5.4-mini`, temperature=0.7, max_tokens=8192
- 이름 유형 감지 → 시스템 프롬프트 선택

## 5. 이름 유형별 생성 흐름

### 5-1. 한자 이름 생성 흐름

```
쿼리 분석 (_resolve_surname)
  ↓
성씨 오행 → Neo4j 상생 체인 조회 (_get_sangsaeng_chain_hint)
  ↓
내부 RAG 에서 hanja_col 로 한자 풀 수집
  ↓
음절 발음 후보 생성 (_generate_sound_candidates, paper_col 트렌드 반영)
  ↓
발음+오행 exact 매핑 → 검증된 한자 풀 구성 (_build_verified_hanja_pool)
  (상극 쌍 사전 제외)
  ↓
_invoke(_GENERATE_SYSTEM)  ← gpt-5.4-mini 이름 생성
  ↓
후처리 파이프라인:
  _fix_broken_headers        ← 헤더 형식 교정
  re.sub 순우리말 헤더 교정   ← [이름 N] → ## [이름 N]
  성씨 한자 괄호 제거         ← (任瑜津) → (瑜津)
  _fix_hanja_headers         ← 한자 → 한글 발음 교정
  _correct_strokes_in_output ← ChromaDB 실제 획수로 교정
  _correct_ohaeng_in_output  ← 상생/상극/중립 판정 교정
  _repair_sanggeuk_names     ← 상극 이름: 대체 한자 교체 또는 제거
  _drop_sanggeuk_names       ← 수리 후에도 상극 남으면 제거
  _drop_duplicate_sound_names ← 동음 중복 이름 제거
  _drop_surname_sound_overlap ← 이름 마지막 글자 발음 = 성씨 제거
  _filter_poor_suri_names    ← 수리 필터 (형격/이격/원격 大凶 제거, 정격 무시)
                               우선순위: 형격 > 이격 > 원격 > 정격
  ↓
검증 (_verify_names → _llm_verify): 부적절 한자 탐지
  ↓
수리 (_repair_names): 동음 후보로 교체
  ↓
후처리 재적용 (_post_repair)
  ↓
면책 고지 추가
```

**시스템 프롬프트 선택 기준:**

| 조건 | 프롬프트 |
|---|---|
| 두 글자 한자 이름 | `_GENERATE_SYSTEM` |
| 외자(1글자) 한자 이름 | `_GENERATE_SYSTEM_SINGLE` |
| 한자 + 순우리말 동시 | 각각 별도 생성 후 결합 |

## 9. 성씨 처리 (`_resolve_surname`)

1. 괄호 표기 우선: `임씨(任)` 또는 `임(任)씨` → 직접 추출
2. 괄호 없으면: `○씨` 독음 확인 → 성씨 뒤 한자 문자 탐색 → Neo4j/ChromaDB로 오행 조회
3. 오행 없어도 한자가 있으면 반환 (clarify 재발동 방지)
4. 성씨 오행 조회 실패 시 `surname_ohaeng.json` (259개 성씨 fallback 사전) 사용

---

## 10. 상생/상극 처리

- `build_graph()` 실행 시 Neo4j에서 동적 로드 (`get_ohaeng_pairs()`)
- Neo4j 실패 시 Python 상수 fallback:
  - 상생: 목→화→토→금→수→목
  - 상극: 목→토, 토→수, 수→화, 화→금, 금→목
- 이름 생성 후 `_correct_ohaeng_in_output()` 으로 상생/상극/중립 재판정
