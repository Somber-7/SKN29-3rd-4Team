# OCR 시도 요약 보고서

## 현행 구현 기준 보완 (2026-06-16)

> 문서 상태: OCR 시도 기록. 현재 운영 RAG 데이터와 직접 동일시하지 않고, OCR 실험/보존 산출물로 구분한다.

현재 Open WebUI -> Pipeline Server -> LangGraph 흐름에서 순우리말 이름 추천에 직접 사용되는 기준 데이터는 `urimalsam_names.json`과 `urimalsam_col`이다. 본 OCR 결과는 해당 운영 컬렉션을 대체하는 데이터가 아니라, 향후 순우리말 후보군을 보강할 때 참고할 수 있는 실험 자료로 관리한다.

| 항목 | 현재 기준 |
|---|---|
| 원본 PDF | `data/raw/pdf/정겨운우리말.pdf` |
| 실제 OCR 산출물 | `data/processed/ocr/ocr_raw_full.txt`, `ocr_structured.txt`, `ocr_clean_log.txt` |
| 현재 없는 파일 | `ocr_cleaned.txt`, `ocr_progress.json`, `ocr_log.txt` |
| 운영 순우리말 RAG | `data/processed/urimalsam_names.json` 301건, `urimalsam_col` 301건 |
| 판단 | OCR 결과는 순우리말 후보 보강 참고자료이며, 현재 운영 RAG의 직접 원본으로 단정하지 않음 |

## 목적

국립국어원_정겨운우리말.pdf (406페이지, 이미지형 스캔본)에서
순우리말 어휘 데이터를 추출하여 RAG 인덱싱 입력 데이터를 만드는 것.

---

## 한계점 및 중단 사유

### 근본적 한계

#### 1. OCR 스캔 품질 자체의 한계
- 대상 PDF가 오래된 이미지형 스캔본으로 인쇄 상태·해상도가 낮아 OCR 인식률이 근본적으로 불안정
- 아무리 정제 규칙을 추가해도 스캔 품질에서 비롯된 오류는 완전 교정 불가

#### 2. 원본 자료 자체의 한계 (2001년 발간)
- 오래된 자료이므로 현재 사용되지 않거나 누락된 순우리말이 다수 존재
- 최신 순우리말 어휘를 망라하지 못해 이름 추천 데이터로서 완전하지 않음

#### 3. 품사 기준 데이터 분리의 어려움
- 이름 추천 목적상 명사형 어휘만 추출하는 것이 이상적이나, 현실적으로 구분이 애매함
- 순우리말 중 형용사·부사로 분류된 단어도 이름으로 사용 가능한 경우가 존재
  - 예: `가분가분 [부]`(가볍고 경쾌한 모양), `가직하다 [형]`(가깝다) 등이 이름 어감으로 쓰일 수 있음
- 단순히 `[명]`만 추출하면 이름 후보에서 유효한 어휘가 제외될 위험이 있어 분리 기준 설정이 어려움

---

### 추가 기술적 한계

#### 4. 한자 인식 불가
- EasyOCR 한국어 전용 모델은 한자를 인식하지 못해 `#`, `@` 등 노이즈 문자로 출력
- 약 1,100개 한자가 미복원 상태
- 해결하려면 PaddleOCR(한자+한국어 동시 지원) 재처리 필요 — 미착수

#### 5. 조사 오인식 잔존
- `를→틀`, `를→름` 등 약 610건이 자동 교정 불가 상태로 잔존
- 앞 문맥이 1글자뿐인 경우 자동 판별 근거 부족 + 오교정 위험으로 의도적 제외

#### 6. 단어 붙음 오류
- 접사 항목의 예시 단어 목록에서 OCR이 줄 바꿈을 무시하고 단어를 연결
- 4건 확인 (`걱정가마리구경가마리...`, `해바라기천둥바라기...` 등)

#### 7. CPU 환경 처리 속도
- GPU 없이 CPU 단독으로 딥러닝 OCR 모델 구동
- 406페이지 처리에 2~3시간 소요 — 재처리 비용 높음

---

### 중단 판단
근본적 한계(스캔 품질, 자료 노후화, 품사 분리 기준 모호)가 추가 정제 작업으로
해소될 수 없다고 판단. 완벽한 OCR 교정보다
다음 단계(ChromaDB 인덱싱) 진행이 프로젝트 일정상 우선순위가 높아 중단.

---

## 의의

- 이미지형 스캔 PDF에서 자동화 파이프라인으로 4,316개 순우리말 어휘 항목 추출 성공
- 반복 적용 가능한 OCR 정제 규칙 12개를 데이터 기반으로 개발
- 추출된 `ocr_structured.txt`는 현재 상태로도 RAG 인덱싱 투입 가능한 형태
- 전체 과정을 `ocr_pipeline.md`에 재현 가능한 수준으로 문서화

---

## 진행 내용

### 1단계 — 텍스트 추출
- EasyOCR (한국어 모델, CPU 전용) 로 406페이지 전체 처리
- 본문(p4~336) 단일 컬럼 / 색인(p340~406) 좌우 2단 컬럼 분리 처리
- 중단 후 재개 가능한 진행 상태 저장 구조 구현
- 결과물: `ocr_raw_full.txt`

### 2단계 — 정제
- 정규식 기반 정제 규칙 12개 개발 및 적용
- 총 12,469건 수정 + 405줄 헤더 삭제
- 규칙 개발 과정에서 false positive 탐지 및 복원 10건 처리
- 결과물: `ocr_cleaned.txt`

### 3단계 — 구조화
- 표제어 [품사] 패턴 기반으로 항목 경계 탐지
- 4,316개 어휘 항목을 항목당 1블록으로 분리
- 결과물: `ocr_structured.txt` (RAG 인덱싱 직접 투입 가능 형태)

### 문서화
- `ocr_pipeline.md` — 전체 파이프라인, 파일별 역할·결과·활용법 기록
