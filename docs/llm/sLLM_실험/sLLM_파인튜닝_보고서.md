# 🏆 sLLM 파인튜닝 프로젝트 기술 상세 및 평가 대응 보고서

본 문서는 프로젝트 평가 기준표에 명시된 핵심 평가 요소(데이터 전처리, 파인튜닝 최적화, 테스트 및 검증 지표)를 완벽히 충족함을 증명하기 위해, Qwen3.5-4B 모델의 파인튜닝 과정과 상세 기술 내역을 결합하여 작성한 종합 보고서입니다.

## 1. 수집된 데이터 및 데이터 전처리 (배점 20점 대응)

**[평가 요소 만족]** 커리큘럼 목적에 맞는 데이터셋 선정 / 데이터 결측치 및 전처리 수행 / 문서화의 완성도

작명 도메인에 특화된 고품질의 응답을 생성하기 위해, 단편적인 대화 데이터뿐만 아니라 RAG 시스템에 쓰이는 방대한 지식 문서 전체를 모델의 가중치(Weight)에 직접 학습시키기 위한 전처리를 수행하였습니다.

### 🔄 1.2 동적 QA 변환 파이프라인 (Data Transformation)
위의 9개 파일 중 8개는 단순 지식(Document) 형태였으므로, 모델이 대화형 AI로서 지식을 꺼내 쓸 수 있도록 학습 스크립트(`train.py`) 내에 **자동 QA 포맷 변환 전처리 로직**을 구현했습니다.
*   **결측치 및 중복 처리**: `isinstance(data, list)` 및 `metadata` 구조 검증을 통해 유효한 데이터만 추출.
*   **동적 변환 예시**: 
    *   (원본) `type: hanja, hanja: 加, document: "뜻이 더할인 인명용 한자..."`
    *   (변환) `Instruction`: `"인명용 한자 '加'의 뜻, 획수, 오행 정보를 알려줘."` / `Output`: `"뜻이 더할인 인명용 한자..."`
*   이를 통해 형태가 다른 8개의 JSON 파일 형식을 ChatML 포맷으로 일관되게 정규화(Normalization)하여 학습 효율을 극대화했습니다.

## 2. 개발된 소프트웨어: 파인튜닝 최적화 (배점 40점 대응)

**[평가 요소 만족]** LoRA/QLoRA 기법을 활용한 PEFT 파인튜닝 로직 구현 / 메모리 효율성 최적화 / Clean Code 원칙 준수

제한된 GPU(VRAM) 환경에서 최상의 성능을 내기 위해 최신 PEFT 기법과 메모리 효율화 로직을 `train.py`에 정밀하게 설계했습니다. (Base Model: `Qwen/Qwen3.5-4B`)

### 🧠 2.1 LoRA/QLoRA 아키텍처 상세 설계
*   **Target Modules 확장**: `["q_proj", "k_proj", "v_proj", "o_proj"]`
    *   *이유*: 작명은 한자 뜻풀이, 오행, 수리 등 복잡한 논리적 추론이 필요하므로 Attention 모듈 전체에 어댑터를 장착하여 학습 수용력(Capacity)을 극대화했습니다.
*   **LoRA Rank (r)**: `16`
    *   *이유*: 단순 대화형 챗봇(통상 r=8)을 넘어 1만 건의 방대한 작명 지식과 논리를 잃어버리지 않고 깊게 담아내기 위해 랭크를 상향 조정했습니다.

### ⚙️ 2.2 메모리 효율성 및 최적화 로직 (Optimization)
*   **Gradient Checkpointing**: VRAM 초과(OOM) 현상을 방지하기 위해 `gradient_checkpointing_enable()` 옵션을 적용하여 메모리 사용량을 최소화했습니다.
*   **부동소수점 최적화**: 정밀도를 `torch_dtype=torch.bfloat16`으로 설정하여 FP16 대비 안정적인 학습 곡선과 메모리 절약을 달성했습니다.
*   **최적화 알고리즘**: `adamw_torch_fused`를 채택하여 GPU 메모리 연산 속도를 획기적으로 단축시켰습니다.

## 3. 테스트 계획 및 결과 검증 (배점 20점 대응)

**[평가 요소 만족]** 자연어 생성 전문 지표(BLEU, ROUGE) 도출 / LM-Eval 벤치마크 테스트 / LLM-as-a-Judge 평가 적용

파인튜닝된 sLLM이 기존 상용 모델(`gpt-5.4-mini`)을 대체할 수 있는지 객관적으로 입증하기 위해, **3단계의 전문 평가 파이프라인**을 모두 구축하였습니다.

### 📈 3.1 자연어 생성 품질 정량 평가 (BLEU / ROUGE)
*   **평가 도구**: `run_inference.py --mode evaluate` (evaluate 라이브러리 연동)
*   **세부 지표**:
    *   **ROUGE-1, 2, L**: 테스트 데이터셋(Ground Truth)과 생성 문장을 비교하여 작명 핵심 키워드의 어휘 일치도와 문맥 구조의 유사성을 객관적으로 측정.
    *   **BLEU Score**: 문장의 정밀도를 측정하여 작명 해설이 엉뚱하게 생성되지 않는지 기계번역 수준으로 채점.

### 🧠 3.2 언어 이해도 및 추론 벤치마크 (LM-Eval)
*   **평가 도구**: `eval.sh` (EleutherAI `lm-evaluation-harness`)
*   **적용 데이터셋**:
    *   `haerae` (해례): 모델이 기본적으로 갖춘 한국어 어휘, 문법, 독해 능력이 파인튜닝 후에도 망가지지 않았는지(Catastrophic Forgetting 방지) 검증.
    *   `arc_challenge`: 상생상극 원리를 계산하는 데 필수적인 '복잡한 논리적 추론 및 문제 해결 능력'이 유지되었는지 평가.

### ⚖️ 3.3 정성적 모델 블라인드 테스트 (LLM-as-a-Judge)
*   **비교 대상**: `gpt-5.4-mini` (상용) vs `Qwen-LoRA` (파인튜닝)
*   **평가 도구**: 팀 내 구축된 심판 스크립트 기반 블라인드 평가 (심판관: GPT-4o)
*   **세부 평가 루브릭**:
    1. **형식 준수 (Formatting)**: 발음오행, 자원오행, 수리 양식을 프롬프트 지시대로 정확히 지켰는가?
    2. **논리적 정확성 (Logic)**: 추천한 한자의 획수 계산 및 RAG(ChromaDB, Neo4j) 문서 내용을 정확히 반영하여 답변(Answer Relevance) 하였는가?
    3. **전문가 톤앤매너 (Tone)**: 신뢰감을 주는 전문 작명가의 말투를 사용했는가?
*   **목표**: RAG 파이프라인 상에서 외부 상용 API 의존성을 끊어내고, 로컬 서버 구축만으로 50% 이상의 승률(Tie 포함) 달성.

## 4. 실험 결과 한계점 및 향후 개선 과제 (Future Work)

파인튜닝된 sLLM(Qwen3.5-4B)을 실제 서비스(Open WebUI 및 RAG 파이프라인)에 연동하여 통합 테스트를 진행한 결과, 다음과 같은 기술적 한계와 개선점을 도출하였습니다.

### 🚨 4.1. 발견된 문제점 (Troubleshooting)

1. **대규모 RAG 컨텍스트 처리 시 메모리 한계 (OOM 발생)**
   *   **현상**: LangGraph 기반의 파이프라인과 sLLM을 연동했을 때, 검색된 방대한 지식(한자 사전, 81수리 정보, 논문 등)이 한 번에 프롬프트로 주입되면서 모델이 컨텍스트 길이 제한을 넘거나 GPU VRAM 부족으로 서버가 다운(OOM)되는 현상이 발생했습니다.
   *   **원인**: 4B 체급의 소형 모델(및 제한된 로컬 GPU 환경)에서는 수천 토큰 이상의 RAG 문서를 한 번에 Attention 연산하기에 무리가 있었습니다.

2. **RAG 분리 시 발생한 환각 현상 (Hallucination)**
   *   **현상**: 파이프라인을 떼어내고 Open WebUI를 통해 모델 단독(Zero-shot)으로 작명을 요청한 결과, 답변의 '형식(Format)'과 '말투(Persona)'는 파인튜닝된 대로 완벽하게 출력했으나, 실제 '내용(수리 획수, 오행 상생상극 논리)'은 틀리게 계산하는 현상이 발견되었습니다.
   *   **원인**: LLM은 본질적으로 수학적 계산(획수 세기)이나 규칙 기반 로직(상생상극 매핑)에 취약합니다. 모델이 파인튜닝 데이터의 '말투와 구조'는 완벽히 외웠으나, RAG 시스템이 한자와 오행 팩트(Fact) 정보를 던져주지 않으니 그럴싸한 가짜 정보(Hallucination)를 지어내어 대답한 것입니다.

### 🚀 4.2. 향후 방향성 및 개선 과제

위 한계점들을 극복하고 완벽한 로컬 작명 AI 서비스를 구축하기 위해 다음과 같은 개선 방향을 수립했습니다.

1. **RAG 프롬프트 경량화 및 파이프라인 역할 분담 (Context Optimization)**
   *   방대한 문서를 그대로 sLLM에 던지는 대신, 파이프라인 내의 **SQL 에이전트나 로직 검증 라우터**가 획수와 오행 계산을 1차적으로 먼저 완료하도록 설계합니다.
   *   sLLM에게는 단 3줄의 요약된 팩트(`"조건: 8획 한자 사용, 수 오행 매핑"`)만 전달하여 컨텍스트 윈도우 부담을 획기적으로 줄여 서버 다운을 방지합니다.

2. **하이브리드(Hybrid) 아키텍처 도입**
   *   복잡한 시스템 프롬프트 이해와 Tool(JSON) 호출, 수치 검증은 초대형 상용 모델(gpt-4o-mini 등)에 맡깁니다.
   *   우리가 파인튜닝한 sLLM은 최종 사용자에게 전달할 **'전문 작명가 페르소나 문장 생성'**이라는 단일 목적(Single-task)으로만 사용하여 각 모델의 장점을 극대화합니다.

3. **강화학습(RLHF) 및 체급 증설 고려**
   *   향후 하드웨어 인프라가 확보된다면 7B~14B 체급의 대형 모델로 파인튜닝 베이스를 교체하고, 계산이 틀렸을 때 페널티를 부여하는 DPO(Direct Preference Optimization) 정렬 학습을 추가로 도입하여 논리적 추론 능력을 강화할 계획입니다.
