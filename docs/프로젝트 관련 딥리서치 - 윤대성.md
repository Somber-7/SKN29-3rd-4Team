# LLM 기반 조건 맞춤형 작명 QA 시스템 아키텍처 및 데이터 파이프라인 심층 분석 보고서

## 도메인 특수성을 고려한 데이터 수집 한계 및 필수 보완 전략

기존 기획안에 명시된 데이터 소스(Unihan DB, 자원오행 분류표, 국립국어원 사전 등)는 시스템의 기초 뼈대를 구축하는 데는 유효하나, 실제 작명가나 역술인이 사용하는 전문적인 작명 논리를 구현하기에는 턱없이 부족하다. 작명은 단순히 글자의 뜻이 좋고 오행이 맞는 한자를 나열하는 것이 아니라, 수천 년간 누적된 사주명리학과 성명학의 엄격한 규칙을 통과해야 하는 고도의 연산 과정이다. 따라서 시스템이 '근거 없는 추천'을 배제하고 전문가 수준의 작명 QA를 수행하기 위해서는 다음의 핵심 데이터 셋이 추가로 확보되고 파이프라인에 통합되어야 한다.

### 획수 연산의 기준 차이: 원획법(元劃法) 데이터의 부재

가장 시급하게 보완되어야 할 부분은 한자의 획수 데이터 기준이다. 기획안은 공개 데이터인 Unicode Unihan DB에서 획수 데이터를 추출하는 방식을 제안하고 있다. 그러나 Unihan DB에 기본적으로 수록된 획수는 현대인이 글자를 쓰는 방식에 맞춘 필획법(筆劃法)을 따르는 경우가 많다. 반면, 한국의 작명소와 성명학계에서는 한자의 원래 부수(部首)가 가진 획수를 기준으로 삼는 원획법(元劃法), 즉 강희자전(康熙字典)에 기반한 정획법(正劃法)을 절대적인 표준으로 채택하고 있다.

성명학에서 원획법을 고집하는 이유는 한자가 가진 본래의 기운과 뜻을 온전히 반영하기 위함이다. 예를 들어, '물 수(水)' 변이 변형된 삼수변(氵)의 경우 필획법으로는 3획이지만, 성명학적 원획법에서는 본래 글자인 水를 기준으로 4획으로 계산한다. 마찬가지로 '마음 심(心)'의 변형인 심방변(忄)은 3획이 아닌 4획으로, '책받침(辶)'은 3획이나 4획이 아닌 본 자인 '착(辵)'을 기준으로 7획으로 계산된다. 만약 시스템이 Unihan의 단순 획수(`kTotalStrokes`)만을 SQLite에 저장하여 수치 조건 필터링(`sql` 노드)을 수행한다면, 이 시스템이 추천한 이름은 오프라인 작명소의 기준과 전면 배치되어 사용자에게 혼란을 초래하고 시스템의 신뢰도를 실추시키게 된다. 따라서 Unihan DB를 파싱할 때 반드시 강희자전 기준 획수(`kKangXi`)를 병합하거나, 국내 작명 학회에서 교차 검증된 별도의 '작명용 한자 원획수 DB'를 웹 크롤링 등의 방법으로 추가 수집하여 통합 JSON에 병합해야만 데이터 결측치와 편향성을 해결할 수 있다.

### 성명학의 핵심 엔진: 81수리(數理) 연산 로직

기획안의 SQLite 수치 조건 필터는 획수의 단순 합산만을 고려하고 있으나, 실제 성명학에서는 이름에 쓰인 한자들의 획수를 조합하여 81수리(數理) 길흉을 판단하는 것이 작명의 성패를 가른다. 81수리는 이름의 성과 이름자의 획수를 더해 원격(元格: 초년운), 형격(亨格: 청년운), 이격(利格: 중년운), 정격(貞格: 말년/총운)의 4격을 도출하고, 이 4개의 숫자가 모두 길수(吉數)에 해당하는지 검증하는 수학적 시뮬레이션 과정이다. 아무리 오행이 상생하고 뜻이 밝은 한자라 할지라도, 이 4격 중 하나라도 흉수(凶數)가 나오면 그 이름은 기각된다. 시스템이 작명소의 역할을 대체하거나 보조하기 위해서는, 사용자가 성씨(예: 김씨, 8획)를 입력했을 때 이 8획과 결합하여 원·형·이·정 4격이 모두 길수가 되는 이름자의 획수 조합(예: 8획-9획-7획 조합)을 사전에 역산(Reverse Calculation)해 내는 동적 연산 알고리즘이 시스템의 백엔드 로직에 구현되어야 한다.

### 불용한자(不用漢字) 및 음령오행 유파 차이 대응

이름에 사용하면 운세에 불리한 작용을 한다고 여겨져 성명학적으로 기피되는 글자인 불용한자(不用漢字) 목록의 수집 및 필터링 적용이 누락되어 있다. 예를 들어, 쇠 철(鐵), 처음 초(初), 가을 추(秋) 등의 글자는 뜻이 훌륭함에도 불구하고 작명에서는 파란만장한 삶을 암시한다 하여 사용을 극도로 꺼린다. 이러한 불용한자 목록은 수백 자에 달하며, 한글 뜻이 좋더라도 한자 자체가 불용한자일 경우 추천 결과에서 즉각적으로 배제해야 하므로, 시스템의 `db_server.py` 또는 ChromaDB 메타데이터 필터링에 블랙리스트(Blacklist) 속성으로 반드시 추가되어야 한다.

또한, 기획안의 리스크 관리 항목에 '오행 유파 기준 상이'가 언급되어 있는데, 이는 주로 발음(초성/종성)을 기준으로 오행을 나누는 음령오행(陰靈五行)에서 발생한다. 한국 작명계는 한글 자음의 오행을 분류할 때 『훈민정음해례본(訓民正音解例本)』을 따르는 유파와 『훈민정음운해본(訓民正音韻解本)』을 따르는 유파로 나뉘어 대립하고 있다. 예를 들어, 'ㅇ, ㅎ'과 'ㅁ, ㅂ, ㅍ'의 오행 배정이 두 문헌 간에 상이하다. 기획안은 자원오행 1가지 기준으로 고정한다고 대응책을 제시했으나, 사용자는 발음오행의 상생 여부를 묻는 질의("김씨 성과 발음 오행이 상생하는 이름")를 던질 확률이 매우 높다. 따라서 시스템은 한쪽 유파를 강제하기보다는, 사용자 질의 시 해례본 기준과 운해본 기준의 결과를 명확히 분리하여 출처와 함께 제공하는 방식이 시스템 아키텍처의 투명성을 높이는 길이다.

## 외부 행정 데이터 소스 탐색 및 획득 파이프라인

기획안은 인명용 한자 규정과 가족관계등록법, 이름 빈도 통계를 위해 외부 API를 연동할 것을 제안하고 있다. 그러나 행정 구역과 대법원 전산 시스템의 데이터 배포 방식은 각기 다른 포맷과 인증 체계를 가지고 있으므로, 데이터 획득을 위한 명확한 파이프라인 설계가 요구된다.

### 대법원 인명용 한자 규정 및 동자/속자 파이프라인

대법원은 자녀의 이름에 무분별한 한자가 사용되는 것을 막고 전산화의 편의를 위해 인명용 한자의 범위를 엄격히 제한하고 있다. 과거 1,000자 남짓이었던 이 규정은 지속적으로 개정되어 최근 1,070자가 대거 추가되면서 총 9,389자로 확대되었다. 이는 일상적으로 사용되는 한자가 사실상 모두 포함된 수치지만, 그럼에도 불구하고 이 범위를 벗어난 한자를 출생신고서에 기재하면 가족관계등록부에 한자가 아닌 한글로만 강제 기록되는 법적 불이익이 발생한다.

이 핵심 데이터를 실시간으로, 혹은 배치 형태로 수집하기 위해 시스템은 대법원 전자가족관계등록시스템(`efamily.scourt.go.kr`)을 모니터링해야 한다. 현재 법원행정처는 이 9,389자의 목록을 정형화된 JSON이나 XML API 형태로 제공하는 대신, 사이트 내 고객센터의 공지사항 게시판을 통해 '인명용한자표 PDF 파일' 형태로 배포하고 있다. 따라서 기획안의 1단계 데이터 수집 방법에서 인명용 한자 규정을 '국가법령정보 API'를 통해 텍스트로 수신한다는 계획은 오류를 내포하고 있다. 법령정보 API는 가족관계등록법 제44조와 대법원규칙 제37조 등의 텍스트 조문만을 반환할 뿐 , 9,389개에 달하는 전체 한자 리스트 부록을 온전히 제공하지 않는다.

이를 해결하기 위해서는 전자가족관계등록시스템의 게시판(게시판 ID: `0000010`)에서 인명용한자표 PDF를 주기적으로 자동 다운로드하는 웹 크롤러를 구축해야 한다. 다운로드된 PDF는 `pdfplumber`를 이용해 파싱하되, 표 형태로 구성된 한자의 폰트 깨짐이나 인코딩 오류가 발생할 수 있으므로 OCR(광학 문자 인식) 모듈을 보조적으로 결합하여 한자 추출의 정확도를 높여야 한다. 또한, 대법원규칙 제37조 2항은 지정된 한자의 동자(同字), 속자(俗字), 약자(略字) 중 별표 2에 기재된 것만 사용을 허락하고 있다. 따라서 수집된 PDF 내에서 본자와 약자 간의 매핑 테이블을 추출하여 Neo4j 지식 그래프의 노드로 병합해야 사용자가 약자로 검색했을 때도 정확한 법적 허용 여부를 반환할 수 있다.

### 법원행정처 공공데이터 (사법정보공유포털) 통계 연동 절차

사용자가 추천받은 이름이 현대에 너무 흔한 이름인지, 혹은 지나치게 희귀한 이름인지를 확인하는 것은 사용자 경험(UX) 측면에서 매우 중요한 가치를 지닌다. 기획안은 이를 위해 법원행정처 이름 통계 API를 연동하고자 하나, 사법부 데이터 시스템의 접근 권한 확보 절차를 프로젝트 초기 로드맵에 반영해야 한다. 이름 빈도 통계는 행정안전부 공공데이터포털이 아닌 대법원이 별도로 운영하는 사법정보공유포털(`openapi.scourt.go.kr`)을 통해 제공된다.

사법정보공유포털의 오픈 API를 활용하기 위해서는 복잡한 승인 절차를 거쳐야 한다. 단순히 포털에 회원가입을 하는 것으로 끝나지 않으며, 오픈 API 신청, 관리자의 승인, 오픈 API 키 발급이라는 다단계 보안 인증 절차가 필수적이다. 공공데이터포털의 즉시 발급 시스템과 달리 사법정보포털은 승인 심사에 며칠이 소요될 수 있으므로, 2주라는 짧은 팀 프로젝트 기간 내에 병목 현상을 방지하기 위해 1주차 Day 1에 가장 먼저 계정 생성 및 API 사용 승인 요청 서류를 제출하는 행정 프로세스가 선행되어야 한다.

### 국가법령정보 실시간 폴백(Fallback) 및 서킷 브레이커 전략

미수집 법령에 대한 질문 발생 시 국가법령정보 API를 실시간 조회하는 폴백 로직은 훌륭한 설계다. 다만, 공공 API의 특성상 일일 호출 제한(Rate Limit)이나 트래픽 과부하로 인한 응답 지연(Latency) 문제가 발생할 수 있다. 최근 오픈소스 커뮤니티에서는 법제처의 수십 개 API를 도구화하여 LLM 환각 방지에 사용하는 `korean-law-mcp` 패키지 등이 개발되어 활용되고 있다. 시스템은 이러한 플러그인을 참조하여 MCP 서버(`law_server.py`)를 구현할 수 있으며, API 통신 모듈에는 반드시 서킷 브레이커(Circuit Breaker) 패턴과 지수적 백오프(Exponential Backoff) 재시도 로직을 적용하여 외부 서버 장애가 전체 RAG 파이프라인의 크래시(Crash)로 이어지는 것을 막는 견고한 예외 처리(Error Handling)를 수행해야 한다.

## 하이브리드 RAG 및 아키텍처 설계의 기술적 고도화

기획안은 ChromaDB(Vector DB)와 Neo4j(Graph DB), SQLite(Relational DB)를 병용하는 하이브리드 접근법을 취하고 있다. 이는 도메인의 복잡성을 감당하기에 가장 이상적인 구조이나, 컴포넌트 간의 인터페이스 및 데이터 흐름을 최적화하기 위해 전처리 및 인덱싱 과정에서 고차원적인 엔지니어링 전략이 반영되어야 한다.

### 최적화된 청킹(Chunking) 및 인덱싱 전략

평가 기준표에 명시된 바와 같이, Vector DB 입력을 위해 문맥을 보존하는 적절한 청킹 전략을 설계하고 문서화하는 것은 RAG 시스템 성능의 핵심이다. 한자 속성, 우리말 이름 사전, 법령 조문이라는 성격이 전혀 다른 세 가지 코퍼스(Corpus)를 동일한 청킹 방식으로 분할하는 것은 치명적인 오류를 낳을 수 있다.

- **구조화된 지식(한자 속성 및 우리말 사전):** 한자의 획수, 오행, 뜻을 담은 통합 JSON이나 짧은 설명이 담긴 우리말 이름 사전은 고정 크기(Fixed-size) 청킹으로 분할할 경우 메타데이터의 연결이 끊어지는 문제가 발생한다. 따라서 이러한 데이터는 문서 분할을 지양하고, 하나의 JSON 객체를 단일 문서(Document)로 취급하여 ChromaDB에 인덱싱하되, 키-값(Key-Value) 쌍을 메타데이터 속성으로 부여하여 임베딩 기반 유사도 검색과 메타데이터 필터링(예: `metadata={"element": "wood"}`)을 결합한 하이브리드 검색을 구현해야 한다.
- **논리적 규범(법령 조문):** 반면, 가족관계등록법 조문이나 대법원규칙은 "제1항의 한자에 대한 동자는 별표 2에 기재된 것만 사용할 수 있다" 와 같이 맥락과 지시 대명사가 조, 항, 호 단위로 얽혀 있다. 이를 단순히 글자 수 기반의 RecursiveCharacterTextSplitter로 분할하면 법적 근거가 훼손된다. 따라서 법령 텍스트에는 의미 기반 청킹(Semantic Chunking)을 적용하거나, 정규표현식을 활용해 조항(Article) 단위의 논리적 경계를 유지하며 문서를 분할하는 맞춤형 파서를 적용해야만 Groundedness(실제성/환각 방지) 평가 요소를 충족할 수 있다.

### Neo4j 지식 그래프 스키마의 확장성

기획안의 Graph DB 스키마는 한자(Hanja)가 오행 카테고리(Category)에 속하고, 법령(Law)에 의해 허용(PERMITTED_BY)된다는 단방향 관계만을 나타내고 있다. 하지만 작명의 핵심은 '관계성'과 '역학적 상호작용'이다. 성명학의 음령오행이나 자원오행은 木(목), 火(화), 土(토), 金(금), 水(수) 간의 상생(相生)과 상극(相剋)이라는 비선형적 관계를 가진다. 예컨대 목생화(木生火: 나무가 불을 살림), 화생토(火生土)는 상생의 길조이나, 목극토(木剋土), 토극수(土剋水)는 상극의 흉조로 피해야 한다.

따라서 Neo4j 노드 간의 엣지(Edge) 정의에 상생상극 논리를 코드 레벨에서 이식해야 한다. `(Category:木)-->(Category:火)`와 같은 상생 관계망과 `(Category:木)-->(Category:土)`와 같은 상극 관계망을 맵핑해두면, "이름 종성으로부터 火生土 土生金 金生水 水生木 으로 상생의 조화가 잘되는지"  확인해 달라는 복잡한 질의에 대해서도 Graph Traversal(탐색) 쿼리 한 번으로 적합한 이름 후보군 필터링이 가능해진다. 이는 연산 자원의 낭비를 줄이고 답변 도출의 레이턴시를 획기적으로 낮추는 아키텍처 설계의 타당성 지표를 극대화한다.

### Multi-Agent 로직: Router와 ReAct 워크플로우

질의 처리의 4단계인 LangGraph 기반 워크플로우 설계에서, 단일 Router 노드가 질문을 4방향(rag, graph, sql, external) 중 하나로 분류하는 것은 지나치게 단순화된 접근이다. 작명을 위한 사용자의 의도는 다중 의도(Multi-intent)를 내포하기 때문이다. "총 획수가 16획이 되면서 출생신고가 가능한 木 오행의 한자 이름을 찾아줘"라는 질의는 한 번에 3개의 도구를 모두 경유해야만 올바른 결론을 도출할 수 있다.

이러한 복합성을 해결하기 위해 에이전트가 사용자의 의도를 스스로 파악하고, 여러 도구를 순차적으로 혹은 병렬로 선택하여 결론을 조립해 나가는 ReAct(Reason + Act) 루프 워크플로우 구현이 필수적이다.

1. **Reason:** 에이전트는 먼저 목표 획수가 16획임을 인지하고 `db_server.py` (SQLite)에 접근하여 획수 조건 한자 풀을 확보한다.
2. **Act 1:** 이 풀을 `rag_server.py` (ChromaDB)로 넘겨 메타데이터 필터를 통해 木 오행 한자만 남긴다.
3. **Act 2:** 최종 남은 한자들을 `graph_server.py` (Neo4j)에 질의하여, 대법원 9,389자 규정에 해당하는 `` 관계가 존재하는지 최종 검증한다.
4. **Final Answer:** 이 모든 경로의 출처(가족관계등록법 제44조 조문 등)를 수집하여 OpenAI API 프롬프트에 결합한 뒤, 출처 라벨이 달린 완성된 답변을 사용자에게 제공한다.
이처럼 컴포넌트 간의 I/O 데이터 포맷과 파싱/라우팅 계층 간 제어 흐름이 명확히 정의된 LangGraph State 객체를 운용해야 무한 루프나 에이전트 마비 없이 안정적인 시스템 구동이 보장된다.

## 언어 모델 파인튜닝(PEFT) 및 프롬프트 엔지니어링 전략

시스템 아키텍처의 후반부인 sLLM 파인튜닝과 답변 생성 계층은 작명 전문 지식을 내재화하여 오픈 API(예: OpenAI) 의존도를 낮추고 시스템 보안성과 독립성을 확보하는 단계이다. 프로젝트 기획안에 명시된 7단계 SLLM 파인튜닝은 평가 기준표의 'SLLM 파인튜닝 및 최적화 코드 역량' 항목을 정조준하고 있다.

### QLoRA 기반 파인튜닝 및 메모리 최적화

EXAONE-3.5-2.4B와 같은 매개변수 규모가 작은 로컬 sLLM이 작명학의 복잡한 논리와 법령 용어를 정확히 구사하기 위해서는 고품질의 Instruction 데이터셋을 구축하여 파인튜닝해야 한다. 작명 조건 QA 데이터셋(Ground Truth QA 셋)을 구성할 때 질문과 단순한 결론 쌍을 넘어, 모델이 내부적으로 추론의 중간 단계를 인지할 수 있도록 연쇄 추론(Chain-of-Thought, CoT) 방식의 프롬프트를 데이터셋에 녹여내야 한다.

파인튜닝 과정에서는 자원 제약을 고려하여 QLoRA(Quantized Low-Rank Adaptation) 기법을 활용한다. 4-bit 양자화를 통해 베이스 모델의 메모리 점유율을 대폭 낮춘 상태에서 작명 및 법령 어휘 패턴을 담은 가중치 매트릭스(LoRA Adapter)만을 업데이트한다. 이때 한자와 법률 용어가 혼재된 데이터 특성상 파라미터 업데이트 시 손실 값(Loss)이 급격히 튀는 그래디언트 폭주(Exploding Gradients) 현상이 발생할 확률이 높으므로, 반드시 그래디언트 클리핑(Gradient Clipping) 기법을 학습 코드에 명시적으로 추가하여 메모리 효율성과 학습 안정성을 동시에 달성해야 한다.

### 동적 파라미터 제어와 출력 파싱(Parsing) 방어벽

응답 생성 시 LLM의 파라미터인 Top P와 Temperature는 사용자의 Use Case에 맞게 동적으로 제어되어야 프롬프트 엔지니어링의 완성도가 높아진다. 만약 사용자가 "어감이 예쁜 순우리말 이름 3가지를 창의적으로 지어줘"라고 질의한다면, Temperature 값을 0.7 이상으로 설정하여 모델의 언어적 창의성을 유도해야 한다. 반면, "가족관계등록법에 의거하여 이 한자가 이름에 쓸 수 있는지 팩트를 확인해 줘"라는 질의의 경우 Temperature를 0.1 이하로 극단적으로 낮추어 법률 정보에 대한 할루시네이션(환각)을 철저하게 방지해야 한다.

더불어 LLM이 답변의 출처를 명시하거나 JSON 형식으로 결과를 반환하도록 지시할 때, 잘못된 출력 형식으로 인해 파이프라인 후단에서 오류(Parsing Error)가 발생하지 않도록 Pydantic 모델과 같은 구조화된 출력(Structured Output) 제약 도구를 프롬프트 계층에 도입하여 예외 처리(Error Handling)를 완벽히 수행해야 한다.

## 정량적/정성적 평가 파이프라인 및 테스트 계획

테스트 계획 및 결과 보고서 작성은 기획된 RAG 시스템이 실제 사용자에게 배포될 수준의 신뢰성을 갖추었는지 증명하는 가장 핵심적인 단계이다. 기획안은 자체 구축한 Ground Truth QA 셋 30~50개를 기반으로 GPT 모델을 심판으로 활용하는 LLM-as-a-Judge 방식을 제안하고 있는데, 이는 최신 NLP 평가 트렌드에 완벽히 부합한다. 평가 기준표를 충족하기 위해서는 다음 세 가지 RAG 전용 평가 지표를 엄밀히 수치화하여 결과 보고서에 담아내야 한다.

1. **Context Relevance (맥락 관련성):** 검색기(Retriever)가 ChromaDB나 Neo4j에서 가져온 텍스트 청크나 지식 그래프 노드가 질의의 의도를 충분히 내포하고 있는가? 성명학의 오행이나 대법원 법령 조항이 질의의 핵심 키워드를 얼마나 잘 커버하는지 평가한다.
2. **Groundedness (실제성 및 환각 여부 판별):** 생성된 답변 내의 모든 사실적 주장이 제공된 검색 문서(오행표/법령 PDF/통계 API 응답)에 100% 기반하고 있는가? 대법원 인명용 9,389자 내에 포함되지 않은 한자를 허용된다고 답변하지는 않았는지 철저하게 검증한다.
3. **Answer Relevance (답변 관련성):** 최종 도출된 답변 내용이 사용자의 원래 질문(예: 획수 16획, 木 오행)에 완벽하게 응답하고 부수적인 정보를 배제했는지 평가한다.

자연어 생성의 유창성 측면을 보완하기 위해 번역이나 요약 과제에 쓰이는 전통적 정량 지표인 BLEU와 ROUGE 스코어를 활용하여, 파인튜닝 전후 모델의 답변 일관성과 핵심 어휘 보존율을 비교 분석해야 한다. 또한, QLoRA로 최적화된 SLLM의 일반화된 언어 능력 손실 여부를 판별하기 위해 LM-Eval(lm-evaluation-harness) 모듈을 이용한 벤치마크 테스트 스코어 보드를 필수적으로 산출해야 한다.

이러한 포괄적 테스트 과정에서 필연적으로 발생하는 시스템의 한계점들, 예컨대 네트워크 지연으로 인한 MCP 라우팅 실패 사례나 동음이의어 한자 처리 과정에서의 레이턴시 급증, 그리고 매우 희귀한 유파의 오행 논리를 묻는 질의에서의 모델 환각 현상 등은 숨기지 않고 테스트 보고서에 가감 없이 기록되어야 한다. 그리고 이에 대한 향후 프롬프트 수정 방향(System Prompt의 Guardrail 강화)이나 추가적인 Instruction 데이터 확보 등의 피드백 및 개선안이 논리적으로 제시될 때, 비로소 프로젝트는 학술적 깊이와 실무적 확장성을 모두 갖춘 완벽한 소프트웨어 산출물로 평가받을 수 있을 것이다.

## 결론 및 실무적 제언

본 보고서에서 분석한 'LLM 기반 조건 맞춤형 작명 QA 시스템' 기획안은 전통적인 성명학의 영역을 현대적 NLP 기술과 외부 데이터 API 파이프라인으로 융합하려는 시도라는 점에서 독보적인 도메인 가치를 지닌다. 하지만 2주라는 제한된 구현 기간 내에 이 시스템이 신뢰성을 확보하기 위해서는, 단순한 글자 매칭을 넘어서 원획법, 81수리, 음령오행 유파, 불용한자 배제와 같은 성명학의 코어 역학적 규칙들을 데이터베이스 구조 및 질의 처리 로직 안에 코드 레벨로 투영하는 데이터 엔지니어링의 정밀화가 가장 최우선 과제로 다루어져야 한다.

또한, 대법원규칙과 가족관계등록법에 의거한 인명용 한자 규정을 시스템에 내재화하기 위해서는 단순한 API 연동을 넘어 전자가족관계등록시스템의 비정형 문서(PDF)를 파싱하여 지속적으로 변경되는 허용 한자 9,389자의 상태 값을 그래프 데이터베이스 내부에 동기화하는 독자적인 수집 파이프라인 확보가 필수불가결하다. Multi-Agent 기반의 ReAct 워크플로우를 고도화하고, 체계적인 LLM-as-a-Judge 지표를 통해 환각을 검증해 낸다면, 본 프로젝트는 향후 법률 자문이나 금융 공시 등 복잡한 제약 조건이 따르는 여타 하이브리드 RAG 솔루션의 아키텍처 레퍼런스로서 기능할 수 있는 강력한 잠재력을 입증하게 될 것이다.
