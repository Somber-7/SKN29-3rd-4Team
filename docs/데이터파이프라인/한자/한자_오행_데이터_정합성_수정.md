## 1. 작업 목적

한자 데이터의 발음오행과 자원오행 값이 일부 잘못 들어간 상태에서는 ChromaDB metadata, Neo4j `Hanja` 노드 속성, Neo4j `BELONGS_TO` 관계가 서로 어긋날 수 있다.

따라서 사용자가 수정한 최종 오행 데이터를 기준으로, 한자 데이터 JSON과 Neo4j 스크립트가 같은 값을 바라보도록 정합성을 맞추는 것이 목적이다.

## 4. 문제 현상

Neo4j 적재 후 관계 수를 확인했을 때 다음과 같은 차이가 발생했다.

| 관계 | 실제 | 기대 | 상태 |
| --- | --- | --- | --- |
| `HAS_SOUND` | 2420 | 2420 | OK |
| `HAS_STROKES` | 2420 | 2420 | OK |
| `BELONGS_TO` | 4843 | 4840 | 확인 필요 |
| `PERMITTED_BY` | 2420 | 2420 | OK |
| `GENERATES` | 5 | 5 | OK |
| `CONTROLS` | 5 | 5 | OK |

`BELONGS_TO`는 한자 1건당 발음오행 1개, 자원오행 1개가 생성되어야 하므로 정상 기대값은 다음과 같다.

```text
2420건 * 2 = 4840건
```

그런데 4843건이 확인되었기 때문에, 3건의 과거 오행 관계가 Neo4j 안에 남아 있는 상태로 판단했다.

## 5. 원인 분석

Neo4j 적재 스크립트는 `MERGE`를 사용해 현재 데이터 기준 관계를 생성한다. `MERGE`는 없는 관계를 새로 만들고, 이미 있는 관계는 유지한다.

문제는 오행 값이 수정된 뒤 다시 적재할 때 발생했다. 예를 들어 어떤 한자의 `resource_ohaeng` 값이 잘못된 값에서 올바른 값으로 바뀌면, 새 관계는 생성되지만 예전 잘못된 `BELONGS_TO` 관계는 자동으로 삭제되지 않는다.

즉, 데이터가 바뀐 뒤 재적재하면 다음 상황이 발생할 수 있다.

```text
기존 잘못된 관계 1개가 남음
+ 새로 맞는 관계 1개가 생성됨
= 한자 1건에 같은 kind의 BELONGS_TO 관계가 2개 존재
```

대표 3건에서 이런 잔여 관계가 발생하여 전체 `BELONGS_TO` 수가 3건 초과했다.

## 6. 해결 방향

최종 기준 데이터는 사용자가 수정한 `hanja_documents.json`으로 정했다. 이후 Neo4j 적재 스크립트에서 현재 값과 다른 과거 오행 관계를 삭제한 뒤, 현재 값 기준 관계를 다시 `MERGE`하도록 보강했다.

적용 방향은 다음과 같다.

1. `Hanja` 노드의 속성은 항상 현재 `hanja_documents.json` metadata 기준으로 갱신한다.
2. `sound_ohaeng` 관계는 현재 발음오행과 다른 기존 `BELONGS_TO {kind: 'sound_ohaeng'}` 관계를 삭제한다.
3. `resource_ohaeng` 관계는 현재 자원오행과 다른 기존 `BELONGS_TO {kind: 'resource_ohaeng'}` 관계를 삭제한다.
4. 삭제 후 현재 값 기준으로 발음오행/자원오행 관계를 다시 `MERGE`한다.

이렇게 처리하면 같은 스크립트를 여러 번 실행해도 잘못된 과거 관계가 누적되지 않는다.

## 8. 후속 사용 방향

오행 값 수정이 발생하면 `hanja_unicode_ohaeng_verified_corrected.json`과 `hanja_documents.json`만 보는 것으로 끝내면 안 된다. ChromaDB와 Neo4j는 이미 만들어진 저장소이므로, 다음 순서로 확인해야 한다.

1. `hanja_documents.json` metadata가 최종 기준값인지 확인한다.
2. ChromaDB `hanja_col`을 필요 시 재생성한다.
3. Neo4j 적재 스크립트를 재실행한다.
4. `BELONGS_TO`가 4840건인지 확인한다.
5. 대표 수정 한자를 직접 조회하여 속성과 관계가 같은 값을 바라보는지 확인한다.

이 원칙을 따르면 오행 데이터 수정 후에도 ChromaDB와 Neo4j가 서로 다른 값을 반환하는 문제를 줄일 수 있다. 운영 Pipeline 관점에서는 `internal_rag` 검색 결과와 `graph_db` 관계 검증 결과가 같은 오행 기준을 바라보게 되어, Open WebUI에 표시되는 최종 답변의 근거 일관성을 확보할 수 있다.
