# 한자 확장 데이터 Document/Metadata 변환 작업 기록

**작성일**: 2026-06-15
**최종 정리일**: 2026-06-16
**작업 범위**: `hanja_documents.json`에 적재되지 않은 한자 6,564건을 별도 JSON으로 정제
**기준 메인 파일**: `data/processed/hanja_documents.json`
**최종 확장 파일**: `data/processed/hanja2_candidate_documents.json`

## 1. 작업 목적

기존 메인 한자 데이터인 `hanja_documents.json` 2,420건은 ChromaDB, Neo4j, 작명 파이프라인의 기준 데이터로 유지한다.

이번 작업은 `hanja.pdf` 원본 범위에서 메인 데이터에 적재되지 않은 한자 6,564건을 별도 파일로 정리해, 이후 ChromaDB 성능 비교 테스트에 사용할 수 있는 확장 데이터셋을 만드는 것이다.

초기에는 검증 등급과 후보 상태를 별도 metadata로 관리했지만, 최종 정리 후에는 `hanja_documents.json`과 같은 document/metadata 구조로 맞췄다. 따라서 기존 파이프라인이나 ChromaDB 인덱싱 로직에서 요구하는 기본 JSON 구조를 깨지 않는다.

## 2. 최종 보존 파일

최종 보존 파일은 다음 2개로 제한한다.

| 구분 | 경로 | 설명 |
| --- | --- | --- |
| 확장 JSON | `data/processed/hanja2_candidate_documents.json` | 메인 JSON과 같은 document/metadata 구조를 가진 확장 한자 데이터 |
| 작업 문서 | `docs/한자_확장_후보군_문서_메타데이터_변환.md` | 생성 목적, 정제 과정, 검증 결과, 후속 ChromaDB 테스트 방향 기록 |

중간 검증 JSON, OCR raw 파일, PDF 렌더링 이미지, 임시 교차검증 보고서는 최종 보존 대상에서 제외했다. 필요한 검증 결과는 이 문서에 요약 기록한다.

## 3. 보존 원칙

| 구분 | 원칙 |
| --- | --- |
| 메인 데이터 | `hanja_documents.json` 2,420건을 기준 데이터로 유지 |
| 확장 데이터 | `hanja2_candidate_documents.json` 6,564건을 별도 파일로 유지 |
| 대체 여부 | 확장 데이터는 메인 데이터를 바로 대체하지 않고, 테스트 후 반영 여부를 판단 |

| 검증용 필드 | `data_tier`, `evidence_grade`, `evidence_status`, `evidence_source`는 최종 JSON에서 제거 |
| DB 적재 | 기존 ChromaDB, Neo4j, MCP server는 이 문서 작성 시점에 수정하지 않음 |

## 4. 최종 JSON 구조

`hanja2_candidate_documents.json`의 각 항목은 메인 `hanja_documents.json`과 같은 구조를 사용한다.

```json
{
  "id": "hanja_OHE2-00001",
  "document": "한자 仮(가)은 뜻이 '거짓'인 인명용 한자이다. 유니코드는 U+4EEE, 획수는 6획, 발음오행은 목, 자원오행은 화이다.",
  "metadata": {
    "type": "hanja",
    "collection": "hanja_profiles",
    "source": "hanja2_candidate_documents.json",
    "profile_id": "OHE2-00001",
    "hangul": "가",
    "hanja": "仮",
    "unicode": "U+4EEE",
    "sound_meaning": "거짓",
    "strokes": 6,
    "sound_ohaeng": "목",
    "resource_ohaeng": "화",
    "is_person_name_hanja": true
  }
}
```

metadata 필드는 다음 12개로 고정한다.

| 필드 | 설명 |
| --- | --- |
| `type` | 데이터 타입. 모든 항목 `hanja` |
| `collection` | 논리 컬렉션. 모든 항목 `hanja_profiles` |
| `source` | 최종 데이터 출처 파일. 모든 항목 `hanja2_candidate_documents.json` |
| `profile_id` | 확장 한자 프로필 ID. `OHE2-00001` 형식 |
| `hangul` | 한자 독음 |
| `hanja` | 한자 문자 |
| `unicode` | 유니코드 코드포인트 |
| `sound_meaning` | 한자 뜻 |
| `strokes` | 획수 |
| `sound_ohaeng` | 발음오행 |
| `resource_ohaeng` | 자원오행 |
| `is_person_name_hanja` | 인명용 한자 여부. 모든 항목 `true` |

## 5. 정제 과정

1. 기존 메인 파일 `hanja_documents.json`은 수정하지 않았다.
2. `hanja.pdf` 원본 범위에서 메인 데이터 2,420건에 포함되지 않은 항목을 확장 데이터 대상으로 분리했다.
3. 기존 후보 JSON의 `뜻 검증대기`, `미검증`, `미확인` 문구를 제거하기 위해 로컬 근거와 외부 한자 자료를 단계적으로 대조했다.
4. 검증 중에는 근거 등급을 `A/B/C/D`로 관리했지만, 최종 JSON에서는 모든 항목이 정제 완료 상태가 되었으므로 등급 metadata를 제거했다.
5. `document` 문장은 메인 `hanja_documents.json`과 같은 문장 구조로 통일했다.
6. `source`는 최종 파일 기준인 `hanja2_candidate_documents.json`으로 통일했다.
7. `毿` 항목은 외부 사전형 근거 기준으로 `毿(삼)`, 뜻 `털이 길`로 수정했다.
8. 기존 ChromaDB, Neo4j, MCP server 관련 코드는 수정하지 않았다.

## 6. 의미 보강 근거

뜻 보강은 임의 추정이 아니라 실제 한자 데이터와 매칭되는 경우에만 반영했다.

사용한 주요 근거는 다음과 같다.

| 근거 | 사용 목적 |
| --- | --- |
| `data/raw/unihan/` | 유니코드, kHangul, kDefinition, 변형 관계, 획수 보조 확인 |
| `data/raw/reference/peoplehanja.json` | 로컬 인명용 한자 뜻/음 보조 확인 |
| `myungcheol/hanja` `hanjaDic.js` | 한자별 한국어 뜻 후보 대조 |
| `hanjadict` 0.4.1 `table.json` | 훈음 기반 한자 뜻/음 대조 |
| Unicode IRG / L2 한자 자료 | 확장 한자 및 변형 관계 확인 |
| 온라인 한자 사전/위키낱말사전 보조 자료 | 로컬/Unihan만으로 부족한 일부 한자 교차확인 |

최종 JSON에는 근거 등급 필드를 남기지 않았지만, 정제 단계에서는 정확한 한자 문자와 독음이 매칭되는 경우만 뜻을 반영했다.

## 8. PDF 교차검증 정리

`hanja.pdf`는 뜻, 획수, 발음오행, 자원오행을 제공하는 사전형 데이터가 아니라 음별 허용 한자 목록에 가깝다.

따라서 `hanja.pdf`는 `sound_meaning`을 직접 채우는 근거로 사용하지 않고, `(hangul, hanja)`가 원본 PDF 범위에 존재하는지 확인하는 보조 검증 자료로 사용했다.

`한글 글자 유니코드.pdf`는 발음오행 산정에 필요한 한글 음절/초성 계열 확인의 보조 자료로 사용했다.

## 9. ChromaDB 테스트 적재 방향

최종 JSON은 메인 `hanja_documents.json`과 같은 구조이므로 ChromaDB 적재 자체는 가능하다. 다만 기존 `hanja_col`을 바로 덮어쓰면 현재 서비스 기준 데이터와 비교 실험이 어려워진다.

따라서 테스트는 기존 ChromaDB와 파이프라인을 보존한 상태에서 별도 테스트 저장소 또는 별도 테스트 컬렉션으로 진행하는 것이 안전하다.

권장 비교군은 다음 3개다.

| 비교군 | 적재 데이터 | 목적 |
| --- | --- | --- |
| Baseline | `hanja_documents.json` 2,420건 | 현재 운영 기준 성능 확인 |
| Expanded | `hanja_documents.json` 2,420건 + `hanja2_candidate_documents.json` 6,564건 | 확장 데이터 전체 포함 시 추천 품질 변화 확인 |
| Hybrid | 메인 2,420건과 확장 6,564건을 분리 컬렉션으로 적재 후 검색 결과 병합 | 메인 데이터 우선권을 유지하면서 확장 데이터를 보조로 쓰는 방식 검증 |

기존 `src/data/index_hanja_chroma.py`는 `data/processed/hanja_documents.json`을 읽고 `hanja_col`을 삭제 후 재생성하는 구조다. 따라서 테스트 단계에서는 이 스크립트를 그대로 실행하면 기존 `hanja_col`이 바뀔 수 있다.

안전한 테스트 방식은 다음 중 하나다.

1. `data/chroma`가 아닌 별도 테스트 경로에 ChromaDB를 만든다.
2. 기존 `hanja_col`이 아닌 테스트 전용 컬렉션명을 사용한다.
3. 임시 테스트 스크립트에서 입력 JSON 경로와 컬렉션명을 인자로 받아 적재한다.
4. 테스트 결과가 확정되기 전까지 `src/mcp/rag_server.py`, `src/graph/naming_graph.py`, `src/data/index_hanja_chroma.py`는 수정하지 않는다.
