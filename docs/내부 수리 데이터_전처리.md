# [1~2단계 완료] 내부 수리 데이터(81suri, yinyang) RAG 청킹 원본 정제 및 외부 API/연산 서버 구축 과정

이 문서는 작명 QA 시스템 기획서의 **'① 외부 문서 API 구축'** 및 **'② 내부 수리: 81suri.json, yinyang.json → RAG 청킹 원본'** 단계에 대해 현재까지 진행된 과정을 기록한 문서입니다.

---

## 1. 외부 API 연동 및 검증 도구 개발 (`law_server.py`)
LLM이 외부 문서를 검색하고 순우리말/법령을 검증할 수 있도록 외부 API와 통신하는 MCP 도구를 구축했습니다.

- **국가법령정보 API 연동**:
  - `search_law(query)`: 사용자가 질문한 법령(예: 가족관계등록법)을 검색.
  - `get_law_article(law_id, article_num)`: 특정 법령의 구체적인 조문(예: 제44조)을 조회하여 정확한 법적 근거(출생신고 가능 여부 등)를 제공.
  - **개선 사항**: 
    - API가 단일 결과를 반환할 때 리스트가 아닌 딕셔너리로 응답하는 이슈를 해결(`_ensure_list` 래퍼 구현)하여 에러를 방지했습니다.
    - 공공 API 서버 불안정 시 HTML/XML 에러 페이지가 반환되어 발생하는 `JSONDecodeError`(ValueError) 예외 처리 로직을 추가하여 시스템 다운을 방어했습니다.

- **우리말샘 API 연동**:
  - `verify_korean_word(word)`: 추천된 이름이 진짜 순우리말인지 사전적 정의와 품사를 조회하여 팩트체크 수행.

## 2. 성명학 수치 연산 서버 구축 (`db_server.py`)
LLM의 취약점인 '수학적 덧셈 및 경우의 수 연산'을 보완하기 위해, 규칙 기반의 연산을 파이썬으로 처리하는 MCP 서버를 구축했습니다.

- **4격(초년/청년/중년/총운) 계산 (`calculate_name_suri`)**:
  - 원격(이름 합), 형격(성+이름상), 이격(성+이름하), 정격(전체 합)의 수식을 성명학 정석 원칙에 맞게 독립적으로 재설계하여 정확도를 100%로 끌어올렸습니다.
  - 연산 결과를 메모리에 캐싱하여 0.01초 만에 오차 없이 계산하고, 길흉(吉凶)을 판정합니다.
- **吉수 조합 역산 (`find_lucky_strokes`)**:
  - 성씨 획수(예: 8획)가 주어졌을 때, 4격이 모두 길(吉)하게 나오는 이름의 획수 조합(예: 10획-7획)을 전부 탐색해 추천.
- **오행 상생/상극 판별 (`lookup_ohaeng_combo`)**:
  - 木火土金水 오행 조합이 들어왔을 때, 각 글자 간의 상생, 상극, 비화(같은 오행) 관계를 판별하고 전체 흐름의 길흉을 반환.

## 3. 내부 수리 데이터 전처리 및 RAG 최적화 (`process_suri.py`)
단순한 형태의 `81suri.json`과 `yinyang.json` 데이터를 벡터DB(ChromaDB)에 최적화된 형태(Document + Metadata)로 정제했습니다.

### 3.1. 81수리 데이터 정제 (`suri_documents.json`)
- **과정**: 각 획수(1~81)의 데이터를 순회하며 빈 데이터를 걸러내고, 설명글을 `document`로 병합.
- **메타데이터 최적화**: 벡터DB의 정확한 필터링을 위해 괄호와 한자를 분리 (예: `"발전격(發展格)"` → `gyeok_ko: "발전격"`, `gyeok_hanja: "發展格"`).
- **결과**: 81건의 독립된 객체 문서 생성 (吉: 47건, 凶: 34건).

### 3.2. 오행 조합 데이터 정제 (`ohaeng_documents.json`)
- **과정**: 125가지의 오행 조합(예: 木水火) 데이터를 순회하며, 각 요소 간의 관계 흐름을 분석해 메타데이터로 부여.
- **분류 세분화 (검색 최적화)**: 기존에 '혼합'으로 뭉뚱그려졌던 조합을 분석하여, 상극이 전혀 없는 조합은 **'부분상생'**, 전체가 비화인 조합은 **'전체비화'**로 명확히 분리했습니다. 이를 통해 향후 LLM이 "상극 없는 좋은 조합"을 필터링할 때 누락 없이 검색되도록 벡터DB 검색 성능(Recall)을 극대화했습니다.
- **도메인 지식 반영**: 같은 오행이 만날 때(예: 木木)의 관계를 성명학 전문 용어인 **'비화(比和)'**로 태깅하여 LLM의 답변 품질을 높임.
- **인코딩 이슈 해결**: 원본 데이터에 섞여 있던 호환용 한자 金(`0xf90a`)을 통합 한자 金(`0x91d1`)으로 전면 정규화(Normalization)하여 매칭 오류 해결.
- **ID 최적화**: 한자로 인한 인덱스 에러를 방지하고 구조적 통일성을 위해 `ohaeng_1`, `ohaeng_2` 형태의 숫자 시퀀스로 고유 ID 부여.
- **결과**: 125건의 오행 문서 생성 (전체상생: 5건, 부분상생: 29건, 전체비화: 45건, 상극포함: 46건).
