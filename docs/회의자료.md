## 2. 💡 회의 안건: 의사결정이 필요한 기술적 쟁점 (Key Issues)

> 혼자서 임의로 진행하기엔 향후 프로젝트 아키텍처와 성능에 치명적인 영향을 미치는 3가지 고민거리입니다. 팀원들과의 명확한 논의와 합의가 필요합니다.

### 쟁점 A: 한자 데이터 전처리 방향성 및 RDB(SQLite) 중복 보존 설계
- **상황**: 현재 4,975자의 `peoplehanja.json`은 아직 전처리가 안 된 원본 상태입니다.
- **고민**: 한자는 같아도 독음(소리)이 다르면 '발음오행'이 완전히 달라집니다 (예: 樂 - 악/락/요). 이 원본 데이터를 딕셔너리 형태로 전처리하여 SQLite에 적재할 때, 단순히 '한자 1글자'를 기준으로 중복을 제거해 버리면 치명적인 도메인 결함이 생깁니다.
- **논의점**: 데이터 전처리를 코딩하기 전에, **`PRIMARY KEY (char, reading, strokes)` 형태의 복합키 구조**를 팀 표준으로 확정해야 합니다. 이 구조가 확정되어야 동음이의어를 훼손하지 않는 완벽한 한자 전처리 스크립트를 안전하게 작성할 수 있습니다.

### 쟁점 B: 2단계 NLP 전처리(KoNLPy) 범위 및 임베딩 모델 선정
- **상황**: 기획서 2단계에 [형태소 분석 → 불용어 제거 → 정규화]가 명시되어 있습니다.
- **고민 1 (어떤 것을 NLP 전처리할 것인가?)**: 벡터 임베딩 모델은 단어가 아닌 '문맥'을 이해합니다. 무작정 모든 불용어(조사 등)를 지우면 검색 성능이 박살납니다.
  - **제안**: 
    - `한자 데이터`: "밝을" -> "밝다"처럼 뜻 검색 매칭률을 높이기 위해 Okt 어간 추출(Stemming)을 적극 적용.
    - `법령 및 운세 데이터`: 불용어 제거 절대 금지. 띄어쓰기 및 특수기호만 교정하는 텍스트 정규화만 적용.
- **고민 2 (어떤 임베딩 모델을 쓸 것인가?)**: RAG 검색의 뇌를 담당할 핵심 모델 선택.
  - **1안**: `jhgan/ko-sroberta-multitask` (무료, 로컬 구동, 빠름, 한국어 준수)
  - **2안**: OpenAI `text-embedding-3-small/large` (유료 API, 다국어 최고 성능, 압도적인 문맥 파악)
  - **논의점**: 일단 무료(1안)로 RAG 파이프라인을 구축해 테스트하고, 최종 평가 단계에서 퀄리티를 위해 유료(2안)로 업그레이드할 것인지 팀원들의 의견 수렴이 필요합니다.

### 쟁점 C: Vector DB(ChromaDB) 아키텍처 및 메모리(OOM) 방어 전략
- **상황**: 앞으로 전처리가 끝난 수리/오행/한자/법령 데이터를 모두 벡터 DB에 밀어 넣어야 합니다. (총합 약 6,000건 내외 예상)
- **고민 1 (환각/노이즈 방지)**: 이 데이터들을 한 컬렉션에 다 때려 넣으면, "재물운이 있는 한자" 검색 시 한자가 아니라 수리 해설이 더 높게 매칭되는 '마스킹 현상'이 일어납니다.
  - **제안**: 컬렉션을 `suri_col`, `ohaeng_col`, `hanja_col`, `law_col` 로 완벽히 분리하고, LLM 라우터가 목적에 맞게 쿼리하도록 설계해야 합니다.
- **고민 2 (데이터 적재 시 메모리 감당)**: 전체 데이터 양이 수십만 건은 아니지만, 로컬 PC 환경에서 한 번에 임베딩 모델을 거쳐 DB에 적재하려고 하면 RAM 메모리 폭발(OOM)이나 시스템 멈춤 현상이 발생할 수 있습니다.
  - **제안**: 앞으로 작성할 Python 적재 스크립트(ChromaDB 및 Neo4j)에 무조건 **`[500건 단위 Batch 처리(Chunking)]` 로직을 필수로 구현**하여 안전하게 메모리를 관리하기로 룰을 정해야 합니다.

- `[ ]` **오전: 위 3가지 기술 쟁점에 대한 팀 합의 및 의사결정 완료**
- `[ ]` **오후 1: 한자 데이터 전처리 및 SQLite 구축**
  - 합의된 복합키(쟁점 A)와 Okt 어간 추출(쟁점 B) 룰을 적용하여 `peoplehanja.json` 전처리 스크립트 개발.

  - OOM 방지를 위해 500건 단위 청크 분할 삽입 적용(쟁점 C).
- `[ ]` **오후 4: 법령 PDF 파서 개발**
  - `pdfplumber`를 사용해 가족관계등록법 PDF를 "제N조" 단위로 분할(정규표현식) 및 정규화(쟁점 B 적용)하는 스크립트 작성.
