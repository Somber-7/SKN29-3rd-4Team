# ChromaDB 기반 수리/오행 데이터 인덱싱 및 검증 보고서

## 1. 개요
본 문서는 작명 QA 시스템의 **3단계 인덱싱 파이프라인** 중, 81수리 및 오행 조합 운세 데이터를 **ChromaDB(Vector DB)**에 적재하고 검색 성능을 검증한 과정과 주요 고려사항을 정리한 문서입니다.

## 2. 구현 내역
* **작업 대상:** 
  * `data/processed/suri_documents.json` (81수리 데이터, 81건)
  * `data/processed/ohaeng_documents.json` (오행 조합 데이터, 125건)
* **사용 기술:** Python, ChromaDB, `sentence-transformers`
* **임베딩 모델:** `jhgan/ko-sroberta-multitask` (한국어 멀티태스크에 특화된 로컬 모델)
* **산출물:** 
  * `src/data/index_chroma.py`: JSON 데이터를 읽어 ChromaDB에 적재하는 인덱싱 스크립트
  * `src/data/test_chroma_search.py`: 사용자의 자연어 질의를 벡터로 변환하여 유사도를 측정하는 검증 스크립트

## 3. 핵심 고려사항 (Design Decisions)

### 3.1. 청킹(Chunking) 배제 및 단일 문서 인덱싱
일반적인 RAG 파이프라인에서는 긴 텍스트를 특정 글자 수 단위로 분할(Chunking)하지만, 본 데이터에서는 **의도적으로 청킹을 수행하지 않았습니다.**
* **이유:** 수리/오행 데이터는 이미 JSON 객체 하나가 완결된 의미(예: 21수 수령격의 전체 설명)를 갖고 있기 때문에, 이를 임의로 분할할 경우 문맥이 단절되어 검색 품질이 하락할 우려가 컸습니다.
* **적용:** 1 JSON Object = 1 Document 로 매핑하여 의미 보존력을 극대화했습니다.

### 3.2. 메타데이터(Metadata) 활용
Vector 검색만으로는 정확한 수치나 범주 매칭에 한계가 있을 수 있습니다. 이를 보완하기 위해 임베딩 텍스트 외에 메타데이터를 함께 저장했습니다.
* **수리 데이터:** `suri_num`, `gyeok_ko`, `gilhyung` (길/흉) 등을 메타데이터로 분리 적재
* **오행 데이터:** `combo`(土火火 등), `flow`(상생/상극 여부)를 적재
* **기대 효과:** 향후 RAG 서버(`rag_server.py`)에서 특정 길(吉)수만 필터링하거나 특정 오행만 가져와야 할 때, Vector 유사도 + Metadata 조건(WHERE)을 혼합한 하이브리드 검색이 가능해집니다.

### 3.3. 컬렉션의 모듈화 및 확장성
ChromaDB 내에서 데이터를 통합하지 않고 `suri_col`, `ohaeng_col` 등 도메인별로 **독립된 컬렉션**을 구성했습니다.
* **이유:** 향후 "한자 속성"이나 "법령 PDF" 데이터가 추가되더라도 기존 인덱스를 건드리지 않고 `hanja_col`, `law_col`만 추가 생성하면 됩니다. 이는 데이터 담당자들의 병렬 작업을 용이하게 만듭니다.

### 3.4. Windows 환경 인코딩 이슈 대응
테스트 스크립트 실행 중 터미널(cp949)에서 이모지 출력 시 오류가 발생했습니다. 이를 해결하기 위해 Python 스크립트 내부에 `sys.stdout.reconfigure(encoding='utf-8')`를 적용하고 이모지를 제거하여 크로스 플랫폼 안정성을 확보했습니다.

## 4. 의미 기반 검색(Semantic Search) 검증 결과

단순 키워드 매칭(BM25 등)이 아닌 문맥을 이해하는 의미 기반 검색이 잘 작동하는지 검증했습니다.

### 테스트 1: 수리 데이터 검색
* **질의:** `"큰 성공과 부귀영화를 누리는 대길수 추천해줘"`
* **결과:** 21수(유사도 0.74), 31수(0.72), 63수(0.70)
* **의의:** '부귀', '대길' 등의 의도를 정확히 파악하여 가장 운세가 좋은 길(吉)수들을 상위에 반환했습니다.

### 테스트 2: 오행 데이터 검색
* **질의:** `"부부 사이가 화목하고 건강하게 장수하는 오행 조합"`
* **결과:** 土火火(유사도 0.74), 火土火(0.73), 火木火(0.72)
* **의의:** 설명문 내의 '백년해로', '가정', '무병장수' 등의 단어들을 질의의 '화목', '건강'과 의미적으로 연결하여 완벽한 조합을 찾아냈습니다.

## 5. 파이프라인 연계 및 향후 과제 (Next Steps)

본 인덱싱 결과는 작명 QA 시스템의 **'사용자 의도 번역기'** 역할을 하게 됩니다. 

1. **RAG Server 연동:** 
   완료된 ChromaDB 컬렉션을 `src/mcp/rag_server.py`의 `search_rag` Tool에 즉시 연동 가능합니다.
2. **LLM 환각 방지:** 
   LLM이 임의로 작명 이론을 지어내지 못하도록, ChromaDB에서 반환된 이 정확한 운세 해설만을 Context로 주입합니다.
3. **DB 연계 (SQLite/Neo4j):** 
   ChromaDB가 "21수가 좋다", "火土火가 좋다"고 판단하면, 이 조건을 SQLite와 Neo4j에 넘겨 실제 해당 조건에 맞는 **한자 목록**을 도출하는 징검다리 역할을 수행합니다.
4. **한자/법령 데이터 인덱싱 대기:** 
   전처리가 완료되는 대로 본 문서의 로직과 동일하게 `hanja_col`, `law_col` 적재 작업을 진행할 예정입니다.
