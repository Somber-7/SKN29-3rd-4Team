## 1. 전체 목적

한자 작명 QA 시스템에서 사용할 원본 한자 후보군을 PDF, Unihan, 오행 자료를 기준으로 수집하고, 정제 수준과 운영 안정성에 따라 A/B/C 후보군으로 나누어 비교 검증하는 것이 전체 작업의 목적이다.

최종적으로 운영 기본값은 A 후보군인 `data/processed/hanja_documents.json` 2,420건으로 판단했다. 원본 범위에서 추가 확보한 6,564건은 `data/processed/hanja2_candidate_documents.json`으로 별도 정리하고, B/C 후보군 비교 검증을 통해 확장 검토 계층으로 관리한다.

이 데이터셋의 역할은 다음과 같이 구분한다.

| 구분 | 파일 | 건수 | 역할 |
| --- | --- | ---: | --- |
| A 후보군 | `data/processed/hanja_documents.json` | 2,420 | 뜻음, 유니코드, 획수, 발음오행, 자원오행이 정제된 운영 기본 후보군 |
| 확장 후보 데이터 | `data/processed/hanja2_candidate_documents.json` | 6,564 | 원본 범위에서 추가 확보한 확장 후보 한자 |
| B 후보군 | 두 파일 합산 | 8,984 | 정제 완료군과 확장 후보군을 한 컬렉션에 통합한 비교군 |
| C 후보군 | A 후보군 우선 검색 + 확장 후보군 보조 검색 | 2,420 + 6,564 | 메인과 후보군을 분리 검색한 뒤 병합하는 검토군 |

핵심 판단은 전체 한자 후보를 처음부터 축소하거나 버린 것이 아니라, 전체 후보군을 정제 수준에 따라 나누어 검증한 뒤 자동 작명 추천의 기본 DB는 A 후보군 2,420건으로 유지하고 B/C 후보군은 별도 검토 계층으로 관리하는 것이다.

## 2. 작업 흐름 요약

한자 데이터 작업은 다음 순서로 진행했다.

```text
원본 한자 후보군 확보
  → 유니코드·뜻음·획수·오행 JSON/CSV 정제
  → 정제 완료 A 후보군 2,420건과 확장 후보군 6,564건 분리
  → 운영 기준 hanja_documents.json 생성
  → ChromaDB hanja_col 인덱싱
  → Neo4j 그래프 적재 및 검증
  → Graph MCP 자연어 조회 구조 보강
  → 오행 데이터 정합성 보정
  → 확장 후보군 hanja2_candidate_documents.json 정리
  → ChromaDB 운영 후보군 A/B/C 비교 검증
  → 운영 기본값 A 후보군 채택, B/C 후보군은 확장 검토 계층으로 보존
```

각 단계의 세부 검증 내용은 원본 MD에 별도 보관되어 있으며, 본 문서는 GitHub 및 평가 제출 시 전체 흐름과 최종 운영 판단을 단독으로 설명할 수 있도록 정리한다.

## 4. 비적용 평가 항목과 사유

평가지표에는 포함되어 있으나, 본 한자 데이터 정제 및 운영 후보군 검증 범위에 직접 적용하지 않는 항목은 다음과 같다.

| 평가 항목 | 적용 여부 | 사유 |
| --- | --- | --- |
| KoNLPy 형태소 분석, 불용어 처리 | 비적용 | 본 데이터는 일반 한국어 문단 코퍼스가 아니라 한자 1자 단위의 구조화 사전형 데이터이므로 형태소 분해와 불용어 제거가 핵심 전처리가 아니다. |
| BoW, TF-IDF, Word2Vec, FastText | 비적용 | 검색 인덱싱은 ChromaDB와 한국어 임베딩 모델 `jhgan/ko-sroberta-multitask`를 기준으로 수행하며, 희소 표현 비교가 본 검증의 중심이 아니다. |
| BLEU, ROUGE | 비적용 | 번역이나 요약 정답 문장과 비교하는 과제가 아니라 작명 추천 QA이므로, 생성 문장의 n-gram 유사도보다 검색 근거성과 환각 여부가 중요하다. |
| LM-Eval | 비적용 | 본 작업은 sLLM 벤치마크가 아니라 데이터 정제, RAG 검색 근거, 후보군 운영 적합성 검증이 목적이다. |
| LoRA/QLoRA 파인튜닝 | 비적용 | 모델 파인튜닝이 아니라 기존 LLM과 RAG/Graph DB 연동 품질을 검증하는 범위다. |
| 멀티모달 평가 | 비적용 | 이미지 생성 또는 캡셔닝 산출물이 아니라 한자 문서/그래프 기반 QA 산출물이 대상이다. |

비적용 항목은 누락이 아니라 데이터 특성과 검증 목적에 따른 범위 제외다. 본 작업의 핵심 평가는 한자별 뜻음, 유니코드, 획수, 발음오행, 자원오행의 정합성과 검색 결과의 Groundedness다.

## 8. Neo4j 그래프 적재 및 관계 검증

ChromaDB가 의미 검색을 담당한다면, Neo4j는 한자와 오행, 획수, 법령 근거 사이의 명시적 관계 검증을 담당한다.

## 13. 최종 운영 판단

전체 후보군을 A/B/C로 나누어 비교한 결과, 운영 기본값은 정제 완료 A 후보군 2,420건을 사용하는 것이 적절하다.

판단 근거는 다음과 같다.

1. 운영 추천에는 검색 범위보다 설명 가능한 metadata 품질이 더 중요하다.
2. A 후보군 2,420건은 뜻음, 유니코드, 획수, 발음오행, 자원오행이 정리된 기준 데이터다.
3. ChromaDB와 Neo4j가 같은 `hanja_documents.json`을 기준으로 구성되어 있어 검색과 구조 검증이 일관된다.
4. B 후보군은 검색 범위를 넓힐 수 있지만, 후보군이 자동 추천 결과에 직접 섞일 경우 설명 책임과 후처리 검증 부담이 증가한다.
5. C 후보군은 후보군을 보조 근거로 활용할 수 있지만, 운영 정책과 노출 기준을 추가로 정해야 한다.
6. 따라서 운영 DB는 A 후보군 2,420건을 기본값으로 두고, B/C 후보군은 별도 검토 계층으로 유지한다.

프로젝트 평가 시 사용할 수 있는 설명은 다음과 같다.

> 전체 한자 후보가 약 9천 건 규모임에도 운영 DB를 2,420건으로 유지하는 이유는 단순 누락이 아니라 A/B/C 비교 검증 결과에 따른 운영 판단이다. 작명 추천은 한자 수보다 유니코드, 뜻음, 획수, 발음오행, 자원오행이 일관되게 검증된 데이터가 중요하다. 따라서 정제 완료 A 후보군 2,420건을 운영용 `hanja_col` 기본값으로 두고, B/C 후보군은 별도 확장 검토 계층으로 유지하는 것이 안정적이다.
